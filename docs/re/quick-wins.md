# Quick wins: skip intro, custom FOV, wheel zoom-out, freecam extras, slider typing

All five items are built without an engine write. The mouse device global is found by input.dll's mouse-init
signature at 0x100011ee (level byte 0x05 pinned).
- (1) **Skip intro** is data only: a logo-less `scr_intro.sc` mounted above `db_zoom_wide`, the same way the
  floating-text fix does. `ui_hdl_intro` then finds no group 1, hides itself on its first update and hands over to
  the main menu.
- (2) **Custom FOV** writes `g_cam_fov` with a fixed value in place of a zoom level. The frustum, ESP, zoom-out and
  freecam all follow it.
- (3) **Wheel zoom-out:** with the stock exclusive DInput mouse the wheel never reaches the game or our WndProc
  during play. The exclusive mouse suppresses `WM_MOUSEWHEEL`, and input.dll drops `DIMOFS_Z`. The wheel is read
  from the mouse device (`GetDeviceState`). The panel runs the engine mouse shared (level 6), so the wheel and
  clicks also reach the window in play (mouse-lock.md "The fix").
- (4) **Freecam extras:** AA's three rows port directly onto our pose. The only engine lever involved was `g_hud`,
  which does not hide the HUD (section 4).
- (5) **Slider typing** is a UI port (entry.h + clipboard). **"Also bound in the game"** is answered live from the
  engine's bind tables through exports (`inp_trigger`, `bind_get`).

Tags: **[D]** decompile, **[A]** disassembly, **[X]** xref, **[S]** string or data file, **[C]** our/sibling source.
Bases: prism3d 0x400000; duke_base, input.dll and dinput8 0x10000000.

## 1. Skip intro

**Facts**
- `game_proc_handler` duke!0x100e0d75 is a state machine [D]. The target state is at `proc+0xcc` and the current
  state at `proc+0xc8`; `FUN_100e0ae0(proc, n)` sets the target. States 1 -> 2 (`loop 0 0`) -> 3 (CD check,
  `ui r :dialog`) -> 4 -> 5.
  - **State 4:** if the requested-map dstring `proc+0x540` is empty, it runs
    `ui s intro:screen:ui_hdl_intro ui/scripts/scr_intro.sc` (S duke!0x101737b8). Otherwise it goes straight to 5.
  - **State 5:** it runs `ui r intro:screen` (S 0x101737a4) and starts the attract demo (`FUN_100e3660`,
    `play demo000 0 1`).
- `ui_hdl_intro` is registered at duke!0x100d9068 with factory 0x100de0f0. Its object is 0x11e0 bytes with vtable
  0x1013aee0 [X, D]. Its methods [A, D]:
  - Init, vt+0x110 (0x100a2a90): caches the text templates of groups 0..31.
  - Show, vt+0x118 (0x100a2b10): zeroes the counters at `+0x11d4/+0x11d8/+0x11dc`, then calls update.
  - Update, 0x100a2c20: advances to group `++[+0x11d8]` through window `vt+0x128(id)`. **If that group does not
    exist, it runs `ui h :screen`** (S 0x10168e9c). Otherwise it fades `+0x11dc` up past 3.5 and back to 0,
    stepping by the frame delta. That is about 7 s per group, if the delta is in seconds.
  - Hide, vt+0x11c (0x100a2b40): calls `FUN_100e0ae0(game_proc, 5)`, which starts the main menu.
  - Event, 0x100a2ba0: event 0xb skips to the next group. It is probably a key or click.
- Data [S, python zipfile]: `scr_intro.sc` lives in db_e01 (stock), db_zoom (Zoom logo, p50), db_wide (p51),
  **db_zoom_wide (p52, regenerated by WideGen each launch)** and the db_lang_* packs (p10). It has two groups:
  - id 1: Sunstorm, ARUSH and 3DR logos;
  - id 2: the Zoom logo.

  No cvar or command skips it. `g_demo` gates only the attract demo; it is in config.cfg, so the game saves it.
- **Ordering, measured in the logs:** engine log line 1328 is our `mount -o ro,p60 .../aspect43/` from
  `floattext_mount()` (probe.cpp:111, first frame). It comes *before* line 1331, `ui s intro:screen...`. So a
  first-frame mount is in place before the intro script is read.

**Mechanism (skipintro.cpp):** a data file plus one mount, as the floating-text fix does (display.md §C, floattext.cpp).
- `duke/base/nukepanel/skipintro/ui/scripts/scr_intro.sc`: one `ui_window` with the stock black background
  child and **no `ui_group`s**. The window must exist, because init, show and update call `vt+0x128` on `[this+0xe4]`.
- When `g_cfg.skipIntro` is set, the first-frame block runs `mount -o ro,p61 "$GAME"/base/nukepanel/skipintro/ /`
  (p61 is above db_zoom_wide's p52). It then logs which archive serves the script, the way floattext.cpp does.
- Show's first update finds no group 1 and hides the window, and hide starts the menu: one black frame.
- Both logo screens are skipped (the script has no groups); the attract demo behind the menu is unaffected.
- Removing winmm.dll restores the stock intro.
- **AA behaviour copied** [C, `aa ui/menu.cpp:2709-2713`, `config.h:31-34`, `skipintro.cpp`]:
  - Settings > STARTUP > "Skip intro" switch, hint "Takes effect the next time the game starts.";
  - persistent in the ini, default off;
  - applied only at the next attach, because the intro has already played by the time the panel exists.

  The row only stores the value.
- **Fallback, if the ordering ever fails:** poll `ui_wget` for `intro:screen` each frame until it appears, then run
  `cmd_execute("ui h intro:screen")`. That goes through the same hide -> state 5 path.

## 2. Custom field of view

**Facts**
- `g_cam_fov` (registered duke!0x100e649e, struct 0x10176fc0, default "50") is the **horizontal** FOV in degrees for
  a landscape screen (render.md §3-4).
  - WideGen writes `uset g_cam_fov "79.7553406"` into `duke/init_widescreen_fov.cfg` at every launch [S]. That keeps
    the vertical FOV at 38.6 deg, as 50 at 4:3 does (Hor+).
  - Our view log shows `fov=79.755` in every level [S nukepanel.log].
- **Nothing but its registration writes `g_cam_fov`** [X: only 0x100e649e references the registration name. The
  player-table name 0x10163cc4 is read only, by `security_camera_build_camera_matrices` 0x10073ccd and
  `FUN_10077b20` 0x10077bb7]. No data script mentions `fov` [S, all zipfs]. It is not in `config.cfg` [S], so a
  runtime value is never saved.
- The camera applies it through a float table: entry {value, name ptr, 0}, with fov at duke!0x10165864
  [A: the bytes at 0x10165834]. Then `rend_projection_change(near, far, fov)` runs if the value differs.
  - **Per-map override:** `actor_camera_build_camera_matrices` 0x1008c4c0 [D] takes a per-server object from
    `FUN_100e7020` 0x100e7020 (list at `game_globals+0x18`). If that object's `+0xf4 != -1`, it re-applies the
    projection with that integer as the FOV (freecam-pause.md section 6 for the far plane).
  - No writer of `+0xf4` was found, and no data file names an FOV.
- **Code:** `zoom.cpp`/`zoom.h`.
  - They cache the stock string while not applying and write `uset g_cam_fov "<v>"` only when it differs by more than
    0.001. On release they restore the exact stock string.
  - They are pinned by the suite (`zoom_should_write`, `zoom_may_recapture`). Custom FOV replaces
    `wantDeg = zoom_fov(stock, level)` with the slider value. Config keys `zoom`/`zoomlevel`/`holdzoom` are orphaned.
- **What follows the FOV automatically:**
  - Frustum culling: `rend_projection_change` marks the frustum dirty (camera-culling.md F1), so culling follows.
  - ESP, offscreen clip and aim: `view.cpp` captures `rend_get_proj_matrix` and `rend_projection_get` at the frame's
    push (view.cpp:141-146), and they all read `view_get`.
  - Zoom-out and freecam: both replace only the view matrix ("the projection is the engine's", view.cpp:190), so they
    combine freely.
  - Security cameras use `g_cam_fov` too, so the custom value applies there as well.
  - Independent of it: the game's own zoom key changes camera distance by x0.5, not FOV (camera-culling.md §4).
- **AA** [C `aa fov.h:21`, `menu.cpp:2385-2397`]:
  - View > FIELD OF VIEW: switch "Custom field of view", hint "Writes the game's own fov. Off gives your value back.";
  - sub-row slider "Field of view", 60..140, default and reset 90, no unit suffix, integer, hint "Wider than the
    game's own menu allows. 90 is stock.";
  - both off by default and persisted, plus a crash stash that restores the player's own cvar;
  - AA's 90 is EDuke32's 4:3-referenced FOV, so the number does not carry over to Prism3D.

**Mechanism:** `zoom_frame` is wired as the FOV owner. While the switch is on, it writes the slider value; when it goes
off, it restores the captured stock string. Everything stays on the main thread. No stash is needed, because
`g_cam_fov` is never saved and WideGen rewrites it every launch. The slider is the engine's own horizontal degrees
on this screen (`FOV_MIN_DEG` 40 .. `FOV_MAX_DEG` 150, stock about 79.8 here); 0 means the captured stock, which is the
reset (`fovOn`, `fovDeg` in config.h).

## 3. Scroll-wheel zoom-out distance

**Facts**
- **The game binds nothing to the wheel.** The key names `mousewheelup`/`mousewheeldown` exist (triggers 270/271,
  prism3d!0x4634a8/0x4636e8 [S], dumps/input-triggers.txt). Neither input.cfg nor config.cfg binds them [S]; the
  weapon keys are `prev`/`next` on num1/num0 and joystick b7/b8.
- **Its only wheel source is `WM_MOUSEWHEEL`.** `prism_wndproc` 0x426340 case 0x20a [D]: while input is active
  (0x43cf71), it posts `inp_event` type 6 (up) or 7 (down) **twice**. `FUN_00407290` [D] toggles the trigger's down
  flag and defers the second toggle to the next frame, which makes one press per notch.
- **input.dll ignores the DInput wheel.** Its buffered mouse read input!0x10001320 [D] handles only `dwOfs` 0/4 (X/Y)
  and 0xc-0xe (buttons 0-2). `DIMOFS_Z` (8) falls to `default` and makes no event.
- **With the stock exclusive mouse in DInput mode (i_grabpointer 1, the Enhanced default), `WM_MOUSEWHEEL` does not
  arrive during play.**
  - The mouse is `EXCLUSIVE|FOREGROUND` (input!0x100011a0).
  - dinput8 registers it for raw input with `0x230 NOLEGACY|CAPTUREMOUSE` (hotkeys.md §2, dinput8!0x100274d8, row 1).
    NOLEGACY suppresses legacy mouse messages, and our input.cpp:299 already notes that the exclusive mouse sends
    none.
  - The raw input goes to dinput8's own window: `hwndTarget = DAT_100310a8`, set in `FUN_1000b48c` [D], probably
    "DIEmWin" (S 0x10002308). It does not go to the game window, so our subclass sees no `WM_INPUT`.
  - The wheel then reaches us only while the device is unacquired: panel open or freecam flying. Then the engine
    ignores it anyway, because 0x43cf71 is clear.
- Consequence: **there is nothing to consume and no conflict with the game.** The problem is reading the wheel at
  all during play.

**Menu:** View > CAMERA, switch "Scroll-wheel zoom" (default off) with the sub-switch "Smooth scrolling" (default on),
next to Zoom out and its "Distance" slider (1..40 m).

**Mechanism (wheelzoom.cpp): read the engine's mouse device.** Call `GetDeviceState` (vt+0x24) on the engine's mouse
device once a frame while it is acquired, and use `DIMOUSESTATE.lZ` (c_dfDIMouse, input-console.md §3). input.dll uses
only buffered `GetDeviceData` (vt+0x28), and immediate and buffered data are separate DirectInput streams.
- The device pointer is the input.dll global read at input!0x10001320 (`DAT_100099ec`). It is located by signature
  scan in input.dll: signature tier, one pointer, no write.
- While the device is unacquired, the `WM_MOUSEWHEEL` our WndProc already accumulates is the fallback.
- Each notch moves the wheel's own pull-back by 1 m, clamped to the Distance slider's range (1..40 m, config.h:86),
  apart from the Distance slider. It is never saved (the saved `zoomoutdist` is the Distance slider's): launch and the Distance reset arrow use `ZOOMOUT_DEF_M`. The
  wheel turned away from you brings the camera closer. The wheel engages the zoom-out view by itself, with the Zoom out switch off.
- **Rejected:**
  - keys instead of the wheel (they would need two more binds);
  - our own raw-input registration: it is process-wide per usage, so it would take the mouse from dinput8;
  - `WH_MOUSE_LL`: a global hook, and the panel never works around security software;
  - `bind_cmd mousewheelup`: the wheel never reaches the triggers with the exclusive mouse;
  - `i_grabpointer 0`: rejected in hotkeys.md.

## 4. Freecam extras (AA rows -> our freecam)

**AA behaviour** [C `aa ui/menu.cpp:2556-2602`, `config.cpp:146-167/344-401`, `esp.cpp:3597-3640`, `campos.h`,
`shot.h`, `input.cpp:554-586/736-751`]:
- **Debug readout**
  - A sub-switch of Free camera, default off, persisted (`freecamdebug`). Hint "Shows the camera's position and
    angle while flying."
  - Drawn only while the camera is live: one line `cam x=%d y=%d z=%d ang=%d horiz=%d` in the engine's units.
    FONT_SMALL, grey 0xFFC8C8C8, outlined, top-left at margin 8, last in the corner stack (`esp_corner_lines`).
  - Its own switch, not the debug log's.
- **Screenshot mode**
  - A sub-switch, default off, persisted (`freecamshot`). Hint "Hides the gun, crosshair, stats, bar and scuba
    mask." Shows "(Unavailable)" when the cvars are unreachable.
  - Active = camera flying && switch && the game's own menu closed. It writes the game's cvars on the edge and
    restores them.
  - It also hides all of our overlays (`shot_hides_overlays`), and it keeps an ini stash so a crash cannot leave
    the cvars off.
- **Copy view key / Paste view key**
  - Binds, defaults B / V (AA config.cpp:400-401), live only while the camera owns input. The key is swallowed.
  - Copy: the published pose goes to the clipboard as `cam x= y= z= ang= pitch=` (Megaton's line, so viewpoints
    cross between the Build games).
  - Paste: searches the clipboard for `cam x=`, parses the 5 fields, checks them (engine bounds, angle ranges), and
    otherwise does nothing and logs one line. The camera flies there next frame. The clipboard is CF_TEXT on the
    window thread (clipboard.h).

**Mapping onto ours** (freecam.h: `FreecamPose { eye[3], yaw, pitch, hand }`, world units at 52/m, Y-up):
- **Debug readout:** a pure line formatter plus one draw in the freecam overlay pass after the crosshair and marker.
  Top-left at margin 8, since our ESP draws no corner lines. Format
  `cam x=%.0f y=%.0f z=%.0f yaw=%.1f pitch=%.1f`, units as in our pose.
- **Copy/Paste** (clipboard.h, campos.h):
  - The line is `dnmp cam x= y= z= yaw= pitch=` in world units (`campos_format`). A Build-game line means nothing
    here: a Megaton line pasted here is refused (no `dnmp cam` tag), not flown to.
  - Paste sets the pose's eye/yaw/pitch and keeps `hand`. Plausibility: finite values and |pitch| <= 89, and within
    `CAMPOS_MAX_UNITS` (past the freecam's far plane nothing draws). No map extent is read.
  - The rows `BIND_ROW_CAMCOPY/CAMPASTE` are in bind.h. **Defaults B (copy) and N (paste):** our camera key defaults
    to V (config.cpp), so AA's V for paste would clash. B and N are unbound in the game [S config.cfg binds].
- **Screenshot mode:**
  - There is no gun or crosshair in this third-person game. The HUD handler
    duke!0x100a1140..0x100a1188 [A] reads `atoi(g_hud)`. The stock binds `-`/`=` set 2 and 1 live.
  - **`uset g_hud "0"` does not hide the HUD** (`uset g_hud 0` in the console mid-level is the same). It only picks the HUD's style (handler 0x100a1140 passes
    `atoi(g_hud) != 0` to 0x100a2840, which calls vt+0x134 on each child window): with 0 the EGO panel goes, the
    weapon, ammo, nuke and J/F/D panels stay. `g_hud` is also saved in config.cfg (`uset g_hud "1"` [S]), so a
    write would need restoring before `cmd_quit` writes the config (hooked where `display_restore_for_quit` runs,
    quit-path.md). Screenshot mode therefore writes no cvar.
  - The HUD is the ui screen `game_view` (class screen, `ui s:l game_view:screen:ui_hdl_hud ui/scripts/scr_hud.sc`,
    duke 0x101744cc). The letterbox hides it with `ui_whide(game_view)` (duke 0x100e7d5f) and shows it back with
    `ui_wshow(game_view, 0)` (0x100e7ddf); Screenshot mode does the same (shot.h). It also hides our crosshair, Duke
    marker, teleport marker, ESP, damage numbers and readout, as AA does.
  - Floating popups (`scr_actor_text`) cannot be hidden without a hook and are left.
  - **Letterbox and level-end stats.** Both are system ui windows made hidden by `ui_create_system_windows` duke
    0x100e0b30 [D]; Screenshot mode hides them too:
    - The bars are `system_03:letterbox` (`ui_hdl_letterbox`, `scr_letterbox.sc`: two black `ui_text` images at
      0-60 and 420-480 of a 640x480 window) [S]. No viewport or scissor: the 3D view stays full screen under them.
      Letterbox start duke 0x100e7d00 shows it and hides game_view; end 0x100e7d70 (states 1/2 only) sets state 3
      and shows it again; the tick 0x100a2e50 (vt 0x1013b010 +0x58) slides 2 -> 1 and, from 3, `ui_whide`s the
      window and goes to 0. State = handler +0x1d4, handler = window +0x21c [D][A].
    - Mission complete is the same letterbox plus `system_game2:partend` (`ui_hdl_part_end`, `scr_part_end.sc`):
      `end_part_activate` 0x100ad290 runs letterbox start, `ui_wshow(partend, 0)` and `ui_whide(game_view)` [D].
      While hidden the stats page cannot be dismissed: its tick (0x100a9ee0 family) returns unless the window is
      visible, so "press to continue" waits until Screenshot mode or the flight ends.
      The page closes through 0x100a9e00 or, on end_part's destroy 0x100ace90, through vt+0x14c = 0x100a9ee0;
      both `ui_whide` it and zero handler +0x1d4, the owning end_part [D][A].
    - Lever: `ui_whide` on each while Screenshot mode is active; at the end shown back with `ui_wshow(w, 0)` only
      if the game still wants it (letterbox state 1-3, partend owner non-zero), else left hidden (a level change
      while flying). The HUD's own rule reads the letterbox state: it leaves game_view to the game only in
      states 1/2 (the end shows it from those). Each handler's vtable slot must hold the read bytes (which name
      +0x1d4) or that window is never hidden (shot.cpp).

## 5. Slider value typing and "Also bound in the game"

**AA** [C]:
- **Typing**
  - `ui/entry.h` (510 lines, verbatim from Megaton) is a pure state machine: open, char, backspace, enter, escape,
    clickaway = commit, caret, selection, copy/cut/paste, with kinds EK_INT/EK_MILLI/EK_METRES. A commit happens only
    when the text differs from the prefill.
  - `menu.cpp:950-961`: a right press anywhere on an enabled numeric row opens the field, prefilled with
    `entry_format(value, kind)`, after committing any other open field.
  - `menu.cpp:1023-1096` draws it: the widest-text well, a C_HAZARD rim, the selection and a blinking caret. It
    commits if the row scrolls out.
  - `input.cpp:590-620, 686` sends WM_KEYDOWN to the field while the panel is open, with Ctrl+V/C/X through
    clipboard.h.
- **The note**
  - `menu.cpp:1470-1477` draws `MENU_GAMECFG_NOTE` = "Also bound in the game" as a dim placeholder row under a key
    row whose VK the game also binds.
  - `gamecfg.cpp` parses EDuke32's `settings.cfg` once per panel open, maps VK to EDuke32's key name
    (`ekm_gamecfg_key_name`), and draws nothing when the file cannot be read.

**Ours:** right-click a slider to type (`ui/entry.h` keyed by VK, with AA's clipboard; only `EK_NONE` and `EK_INT` are
defined; the open, draw and commit sit in `row_slider_at`) and the note row under a key row the game also binds, read from the engine's live trigger and bind tables
(`gamebind.h`). `g_ui.rpressed` is panel.cpp:87-89. Metre rows (zoom-out distance, flight speed) are stored in
metres already, so `EK_INT` covers every slider; EK_METRES and EK_MILLI are left out.

**How to know a VK is bound in this game (live, exports only plus two proven struct offsets)**
- Triggers are 333 records of 0x240 bytes at prism3d!0x43d528. `inp_trigger(i)` 0x407110 returns `0x43d528 + i*0x240`
  [D]. The record starts with the key name: `inp_trigger_name(name)` 0x407120 compares the record pointer itself
  [A 0x407130]. Names by index are in dumps/input-triggers.txt.
  - 0-255 are DIK scan codes;
  - 262-266 are mouse1-5 (in DInput mode: mouse1 = left, mouse2 = right, mouse3 = middle, from input!0x10001320's
    offsets 0xc/0xd/0xe; window-message mode swaps 2 and 3, prism_wndproc 0x204/0x207);
  - 270/271 are the wheel.
- **Command binds:**
  - `bind_get(keyName)` 0x4063d0, cdecl, one stack argument [A 0x4063d2]. It returns the 0xa8-byte bind record from
    the table 0x476590..0x480d90, or 0. The record holds `+1` key[32], `+0x21` command[128] and `+0xa1` always.
  - `bind_add_cmd` 0x406410 [D] also stores the record at `trigger+0x40`.
- **Impulse binds:** `bind_add_imp` 0x406490 [D] writes the impulse pointer to `trigger+0x44+slot*4` (slots 0-3).
  The all-export alternative is `inp_trigger_impulsealias(alias, slot, prevTrigger)` 0x407190, which iterates the
  triggers bound to an alias. It is decompiled as thiscall with ECX leaked: read its entry before calling.
- **VK -> trigger index:** `MapVirtualKeyW(vk, MAPVK_VK_TO_VSC_EX)`, with an E0 prefix giving `DIK = sc | 0x80`.
  Special cases: VK_PAUSE and VK_NUMLOCK are swapped relative to DIK, and generic VK_SHIFT/CONTROL/MENU map to the
  left key. Our mouse bind codes map to 263/264/265/266 (right, middle, X1, X2). In DInput mode mouse4/5 never
  fire, because input.dll handles buttons 0-2 only.
- **Cost:** one VirtualQuery over the trigger range (0x43d528..0x46c268, static prism3d .data) per panel open, then
  plain reads: one guarded range, not one read per key (a guarded read costs ~12 us here).
- Alternative not taken: parse the `bind_cmd`/`bind_imp` lines of duke/base/config.cfg, as AA parses settings.cfg. It
  is simpler, but stale until the game rewrites the file.
- Current binds to know about [S config.cfg]:
  - letters w a s d z x;
  - Space, LCtrl, LAlt, RCtrl, the arrows, 0-9, num0-9;
  - F1, F5, F9, F10, F11, Esc, backquote, `-`, `=`;
  - mouse1 and mouse3.

  So our defaults Insert, V and T are free.

## 6. Freecam wheel FOV

While the freecam flies, the wheel steps the FOV 2 degrees a notch (40-150, the Custom field of view range) and
owns `g_cam_fov`; away from you narrows, like a zoom-in. One owner of `g_cam_fov` per frame: the flying wheel, then
Custom FOV, then the stock (freecamfov.h, zoom.cpp owner, wheelzoom.cpp notches). Verified in game. While the
camera also pauses the world, the pushed projection follows `g_cam_near` and `g_cam_fov` (freecam-pause.md section 6).
